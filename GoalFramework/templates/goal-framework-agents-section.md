# Goal Framework 项目规则

项目通过三层文件管理：项目总纲、活跃目标、已归档目标。

## 开始工作

1. 阅读 `docs/PROJECT.md` 和 `docs/CURRENT.md`。
2. 若工作属于活跃目标，阅读 `goals/active/` 中对应的文件。
3. 若目标关联了 `docs/technical-plans/` 中的技术方案，编码前按目标中的顺序全部阅读。
4. 修改前简要说明要推进的目标及当前状态。

## 对话变更与确认同步

推进活跃目标时，主动将用户反馈与目标及全部关联技术方案比较。目标目的、交付范围、完成条件，或方案的关键技术决策、实施步骤、验证方式发生实质修改或新增要求时，必须提醒用户选择，不等待用户另行要求同步文档。

1. 探索性提问、备选方案和措辞调整不直接触发同步。形成具体调整后合并提醒，最迟在依赖该调整的实施开始前或本轮讨论结束时提出；目标无法唯一定位时先确认关联对象，没有活跃目标时不自动建立目标。
2. 确认前读齐相关目标和全部关联方案，列出“原记录 → 新约定”（新增要求标明原先未记录）、受影响文件及需重新验证的完成条件。只有长期边界或原则受影响时，才将 `docs/PROJECT.md` 纳入确认。
3. 明确提供三个选择：**采用新约定并同步**（更新后按新约定推进）、**保留原约定**（不采纳本次调整，按旧记录推进）、**继续讨论**（暂不改写约定，暂停依赖分歧的实施，其他工作可继续）。
4. 即使用户说“就改成 B，按这个做”，若未明确授权同步记录，仍须确认一次。选择“采用新约定并同步”或明确要求同步该变更，即构成相关文档更新授权；直接完成同步，不再索要一次写文件指令。同一已授权变更不重复确认，后续新增差异再次确认。
5. 同步前运行 `goal-framework doctor`；仅修改受影响章节，保留无关内容、有效证据及现有文档格式。范围或验收标准变化时调整完成条件，重新核验含义改变的已完成条件；证据不足的恢复为未完成，并重新汇总父条件。正文及完成条件修改可直接编辑；已有命令支持的进度、关联与全局状态维护使用 `checkpoint`、`plan attach/detach` 等命令，检查点记录已确认的变更结论而非聊天全文。
6. 没有技术方案文档时不自动创建；确需新建留档时，将拟创建路径明确列入本次确认，获授权后按下述留档流程保存与关联。
7. 更新后运行 `goal-framework doctor`，报告修改文件、关键变化和检查结果。部分更新失败时说明已同步与未同步部分，暂停依赖文档一致性的实施。`doctor` 只检查结构与链接，不验证对话语义一致性；Agent 仍需核对更新内容是否符合用户确认。

## 技术方案留档

普通的方案讨论、评审或头脑风暴不代表用户授权写文件。当用户明确要求保存、留档、落盘或归档技术方案（或表达等价意图），或在上述同步确认中授权新建方案时，必须完成以下流程；已授权的已有方案更新按上述同步流程完成：

1. 将当前已确认的方案整理成可独立阅读的内容；保留关键取舍、实施步骤、验证方式和待确认事项，不复制完整聊天记录。
2. 若目录不存在则创建 `docs/technical-plans/`，再以描述性文件名写入 UTF-8 Markdown 文件 `docs/technical-plans/<name>.md`。
3. 除非用户明确要求更新已有方案或已确认同步该方案，否则不得覆盖已有文档；发生重名时使用新的描述性文件名。
4. 若能够唯一确定对应的活跃目标，写入成功后执行 `goal-framework plan attach <goal> <document>`；没有目标或目标不明确时，不猜测关联对象，先报告文档已保存但尚未关联并请求用户指定。
5. 运行 `goal-framework doctor`，然后向用户报告技术文档路径、关联目标（如有）及检查结果。

## 维护规则

- 若环境提供 `goal-framework-operator` skill，目标的新建、检查点、检查和归档优先使用其 Python `goal-framework` 命令；不要简写为 `goal`，以免与 Agent 自身的目标功能混淆。
- `docs/PROJECT.md` 只保存长期愿景、目的、边界、原则与阶段方向。
- `docs/CURRENT.md` 是唯一的全局当前状态；只列活跃目标、阻塞项和下一步。
- 需要独立推进、探索或验收时，创建一个目标文件。目标可为“交付型”或“探索型”。
- 复杂目标的完成条件可使用每级两个空格缩进的嵌套复选框。叶子条件必须可独立验证；父条件只汇总直属子条件，所有子条件满足后才自动满足。进度按叶子条件统计。
- 技术方案使用自由格式 Markdown；按上述留档或确认同步流程创建或修改，不预建空文档。
- 目标可关联零到多份技术方案。优先使用 `goal-framework plan attach/detach` 维护链接，不要删除或移动技术文档来解除关联。
- 已关联的技术方案是编码依据；若方案与目标、代码或配置现状冲突，先向用户说明并协调更新，不得静默偏离方案。
- 活跃目标文件命名为 `YYYY-MM-DD-short-title.md`：使用创建日期、小写英文短标题和连字符，例如 `2026-08-12-time-tracker-v01.md`。
- 归档目标使用归档日期命名：完成后将文件重命名为 `YYYY-MM-DD-short-title.md`，其中日期为归档日期，再移至 `goals/archive/`；例如 `2026-09-01-time-tracker-v01.md`。
- 目标完成后，在目标文件写明结果、验证或结论，再移至 `goals/archive/`。
- 只记录可复用的事实和结论，不记录完整聊天过程或敏感数据。
- 文档与可验证的代码、配置冲突时，以代码和配置确认当前事实；若冲突涉及已关联技术方案，按上述规则先向用户说明并取得更新授权，不得直接改写方案或静默偏离。
